# 기존 목표값 처리 검토

실제 수행은 코드·읽기 점검·오프라인 계획·모의 테스트까지다. 별도의 현장 전용 목표 초기화 기능은 추가했으며 실제 모터 쓰기는 실행하지 않았다.

## 확인된 근거

- 직전 실제 읽기에서 현재 원시 위치는 [2065,847,3082,2575,1812,530], 기존 목표는 [0,0,0,0,0,0]이었다. 이후 값은 새 교차검증 결과로 확인한다.
- LeRobot의 보정은 파일과 모터의 보정값을 비교하는 기능이다. home 정렬과 보정 일치만으로 목표 레지스터가 현재 위치로 초기화되지는 않는다.
- [제조사 SDK](https://github.com/ftservo/FTServo_Arduino/blob/main/src/SMS_STS.cpp#L22-L35)의 위치 쓰기와 [토크 제어](https://github.com/ftservo/FTServo_Arduino/blob/main/src/SMS_STS.cpp#L114-L117)는 별도 함수다. 이것만으로 이번 모터 펌웨어에서 목표 쓰기가 토크 상태에 영향을 주지 않는다고 보장할 수는 없다.
- 현장에서는 이전 목표 쓰기 뒤 통신 오류와 토크ON 관측이 있었다. 인과관계와 펌웨어 동작은 미확인이다. 자동 목표 수정이나 단순 재시도를 하지 않는다.

## 이번 도구

- `goal_crosscheck.py`: 기존 읽기 보호와 RobotController를 재사용해 같은 버스에서 개별 READ와 SYNC_READ의 Goal_Position을 비교한다. 토크ON 또는 온도45°C 이상이면 추가 serial 읽기를 중단한다. 카메라·모델 추론·모터 쓰기 없음.
- `goal_initialization_plan.py`: 보정·상태·개별/동기 읽기 일치가 확인된 보고서에서 현재 원시 위치를 제안값으로 정리한다. degree를 원시값으로 재변환하지 않는다. `execution_authorized=false`인 검토표만 생성한다.
- 기존 `operator_arm.py`의 정확한 목표 일치·전체 토크OFF·home·온도 조건은 그대로 유지한다. 새 계획 도구가 그 검사를 해제하지 않는다.
- `operator_candidate/initialize_current_goal.py`: 현장 입회와 팔 지지, 직접 입력이 있을 때만 현재 위치에 해당하는 정확한 Goal 패킷1개를 허용한다. 다른 쓰기·재시도는 차단한다. 실제 실행은 NOT_RUN이다. FIELD_GUIDE.md를 함께 읽는다.

## 현장 검증이 남는 이유

목표 초기화 자체가 모터 쓰기다. 현장 입회·팔 지지·전원 차단 수단, 송신할 정확한 패킷 검토, 쓰기 직전/직후 토크 상태 확인이 필요하다. 여러 레지스터를 한 패킷에 넣으면 물리적으로 안전하고 원자적이라고 가정하지 않는다. 이번 자동 작업에서는 이 동작을 실행하지 않는다.

현재 사용자가 실행할 초기화·토크ON 명령은 없다. 읽기 및 모의 테스트 결과와 실행 허가를 구분한다.
