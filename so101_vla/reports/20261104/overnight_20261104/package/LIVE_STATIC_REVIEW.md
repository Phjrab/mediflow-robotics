# v4 live 정적 검토와 v5 제안

검토 대상은 기존 v4이며 SHA256 `af72d76b992c237211c576796219694503986609277da9b877913b550df6ec56`이다. 파일을 수정하지 않았다. 무인 상태에서 live는 실행하지 않았다.

## 남은 문제와 제안

1. **HOLD도 모터 쓰기다.** 토크OFF/일부ON/모드·현재 위치 미확인일 때 현재 위치 Goal을 쓰면 토크가 재활성화될 수 있다. 이런 fault에서는 추가 Goal 쓰기를 하지 않고 마지막 목표 상태를 보고해야 한다. 토크를 끄는 자동 fallback도 넣지 않는다.
2. **동기 추론 중 안전 감시 공백:** 현재 약3초 지연이50/30=1.667초 소비시간보다 길다. 독립된 정지 수단과 감시·정책 계산의 분리, 동일 serial 단일 소유, 신선도/timeout 규칙이 필요하다. 이것은 RTC/async 구현을 완료했다는 뜻이 아니다.
3. **영상 검사 한계:** v4는 두 시점 hash 반복 후보를 본다. 실제 producer timestamp·카메라간 skew·암부/불량 영상 검사는 없어서 현재처럼 어두운 영상의 의미적 품질을 보증하지 못한다.
4. **누적 clip 감시 없음:** 지속적으로 잘리는 정책을 정상 동작처럼 숨길 수 있다. clip 비율을 기록하고 반복 초과 시 중단하는 제안을 추가했다.
5. **절대 관절 한계/하드웨어 정지 버튼/RobotController 경로:** 기존 단일 제어 경로 통합과 독립 정지 버튼은 미충족이다. 모터 보정 범위를 충돌 없는 물리 경로로 간주하지 않는다. 확인된 절대 한계 없이 임의 값은 넣지 않는다.
6. **max_seconds는 독립 watchdog이 아니다.** 초기 연결/동기 GPU 호출에 별도 상한과 정리 보장이 필요하다. 무인 dry 작업에는 외부 timeout을 사용하되 이를 live 안전 장치로 대신하지 않는다.

20도/초 검사는 전송 목표 시퀀스의 설정 제약이다. 실제 관절 속도·가감속을 측정한 결과가 아니며,0.5도×30Hz=15도/초 계산만으로 물리적 최대속도를 보장하지 않는다. 부하/Status<기존한계 검사도 v5 제안에서 유지하며, 값이 미확인이면 HOLD한다.

## 별도 v5 파일

`so101_first_action_test_v5_proposal.py`는 **순수 안전 판정 제안 모듈이며 실행기가 아니다.** 기존 v4를 바꾸지 않는다. 장치 import/serial/모터 전송 기능이 없고, 결과는 항상 `register_writes=0`이다.

- 모델·단위·카메라·LIVE 확인이 없으면 HOLD.
- 6개ON/위치모드0/시작<50/55정지/home±5/첫목표10/0.5cap/20도/초를 유지한다.
- 신선도 기준이 미확인이거나 초과, 추론이 chunk 소비시간 초과, 정지 요청/시간 초과, 누적 clip 초과이면 `HOLD_NO_WRITE`를 반환한다.
- 신선도 테스트의0.5초는 합성 테스트 값이며 현장 승인된 설정이라고 보고하지 않는다.
- 실제 RobotController 통합·모터 실행·독립 watchdog·정지 버튼 검증은 NOT_RUN이다. G5/G6 통과로 쓰지 않는다.

무인 공통 읽기 계층은 토크0만 허용하고45°C에 중단한다. v5의 현장 live 판정(토크6개ON,50/55°C)과 혼용하면 안 된다. 현장 입회 프로파일은 별도 설계·검증이 필요하다.
