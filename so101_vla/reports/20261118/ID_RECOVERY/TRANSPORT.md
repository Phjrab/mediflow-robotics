# ID 불일치 수신 복구 — 소프트웨어 검토

2026-11-18. 이 변경 및 검증에서는 실제 모터 접근·목표·토크·설정 쓰기와 live 실행을 하지 않았다. 보정, P/I/D, 가속도, 홈 허용값, 그리퍼 48.5점, 집기 오른쪽 +6틱, speed 0.33 및 READY 이후 제한 시간은 변경하지 않았다.

## 확인한 실패 경로

19:35:16 실기 검토에 기록된 패턴은 첫 ID1 읽기 timeout 뒤 ID2 수신 자리에서 ID1, 이후 축들에서도 앞선 응답이 밀리는 현상이다. 수신된 패킷 자체의 체크섬은 유효했다. 기존 `parse_reply`는 올바른 형식의 다른 ID 응답을 비재시도 오류로 분류했고, 상위 실행기가 `wire_fault`를 설정하여 위치 유지 재시도까지 막았다.

이는 **지연 응답으로 어긋난 수신 순서와 복구 경로 부재**를 설명한다. 최초 지연을 일으킨 물리 원인이 제어보드·전원·배선·USB·OS 스케줄링·기록기 부하 중 무엇인지는 이 코드 검토나 모의시험으로 확정하지 않는다. 과거 로그에는 당시 CPU 점유율이 없으므로 실측 CPU 수치를 만들어 제시하지 않는다.

## 변경

- 새로운 읽기 요청 직전 `serial.reset_input_buffer()`와 남은 RX 바이트 소진. 정상 SYNC_READ의 6개 응답 사이에서는 초기화하지 않는다.
- 올바른 헤더·길이·체크섬을 가진 다른 ID 패킷은 값을 사용하지 않고 폐기한다. SDK 통신 코드가 0뿐 아니라 -6/-7이어도 ID 불일치를 별도로 집계한다.
- SYNC_READ 배치가 어긋나면 남은 배치 응답을 폐기하고, 실패·미수신 축을 같은 주소와 길이의 새 개별 READ로 조회한다. 다른 ID의 값을 현재 축 값으로 재지정하지 않는다.
- 기존 주기 내 최대 3회 재시도, 연속 5회 실패 및 정상 응답 없이 200ms 중단 예산을 유지한다. 재동기화 대기도 이 시간에 포함된다.
- 위치 유지 복구는 기존 최대 5회 안에서 매번 현재 위치를 새로 읽고, 유지 목표 쓰기 직전에 RX를 초기화한다. 실제 목표 readback과 안정 확인 후에만 `HOLD_CONFIRMED`가 된다.
- `communication.id_mismatch_by_joint`, `by_joint.*.id_mismatch`, `input_flushes`, `discarded_rx_bytes`를 summary에 추가했다. 비어 있는 버퍼 초기화마다 로그 행을 추가하지 않아 정상 주기의 로그 증가를 줄였다.
- 진짜 모터 상태 오류 및 유효하지 않은 헤더/길이/체크섬은 정상 상태로 사용하지 않는다.

## 검증

Windows의 실제 실행기 수신·재시도 함수에 가짜 포트와 시간을 연결했다. ID 복구 9개, 기존 통신 10개, 그리퍼 보호 13개, direct 실행기 모의 4개: **36개 PASS**.

| 상황 | 검증 결과 |
|---|---|
| ID1 timeout → ID2 자리의 늦은 ID1 | 현재 배치에서 두 패킷만 읽고 잔여 폐기, 1/2/3/4/6/5 새 읽기, 축별 값 정확 |
| 통신 성공인데 다른 ID | 패킷 폐기, 동일 READ 재전송, fault 영구 래치 없음 |
| -7이며 다른 ID의 유효 패킷 | -7과 ID 불일치 각각 집계, 잘못된 값 미사용 |
| 정상 6축 SYNC_READ | 새 요청 전 초기화 1회, 응답 사이 초기화 0회 |
| 다른 ID 응답 5회 지속 | 5번째 실패에서 HOLD |
| 마지막 정상 응답 190ms 후 11ms 지연 | 200ms 예산 초과 HOLD, 재시도 때문에 기한 연장 안 됨 |
| 온도 20ms 간격 대기 중 지연 패킷 유입 | 대기를 먼저 끝내고 송신 직전 RX 초기화하여 늦은 패킷 미사용 |
| 위치 유지 목표 확인 불일치 | 버퍼 초기화 뒤 최대 5회 시도, `HOLD_NOT_CONFIRMED` |
| 실제 상태 코드 및 체크섬 훼손 | 정상값으로 통과하지 않음 |

`tools/recorder_bus_readonly.py`의 추가 모의 **6개 PASS**: READ 외 패킷 거부, 6축/토크/온도 조건, 기록기 오류 및 close 실패 시 정리, 버스 종료의 직접 포트 close 경로. 이 도구는 `(33,8)`, `(56,15)`, `(63,1)` READ만 송신할 수 있다. `connect(handshake=False)` 후 독점 포트 잠금, 토크 OFF 확인, live와 같은 fresh 개별 온도 읽기·20ms 간격·모드 캐시 최대 50ms·200ms 통신 watchdog을 사용한다. 로봇/버스의 토크 종료 함수를 호출하지 않고 포트를 직접 닫는다.

## 실제 A/B 비교의 범위와 미완료 사항

준비한 도구는 같은 저장 RGB 영상 3장을 사용해 링버퍼 OFF/ON 각각 60초의 버스 읽기 지연, ID 오류, 주 프로세스 CPU 및 기록기 프로세스 CPU를 비교한다. 카메라 실시간 취득·모델 추론·모터 목표 쓰기는 포함하지 않으므로 전체 live 부하와 동일하다고 표현하지 않는다. 진단 자체는 raw 또는 개별 55°C를 즉시 중단하며 live의 2초 온도 판정을 변경하지 않는다.

**실제 Jetson/서보 A/B 측정은 이 보고서 작성 시 NOT_RUN이다.** 준비된 코드와 모의 결과를 실제 60초+60초 결과로 대체해 보고하지 않는다. 실제 버스 지연 영향이 0이라는 보증도 하지 않는다.
