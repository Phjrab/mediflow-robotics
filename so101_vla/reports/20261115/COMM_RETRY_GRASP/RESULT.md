# 통신 복구·집기 실패 분석 — 2026-11-15

실제 live는 실행하지 않았다. 모터 검사는 READ만 수행했고 목표·토크·설정 쓰기는 모두 0회다. 보정/PID/가속도와 모델·학습 원본은 변경하지 않았다.

코드 커밋: Windows `16112de`, Jetson `751ffb8`, 기존 작업 브랜치 `vla/fast-track`. push하지 않았다. 두 장치의 변경 소스 12개 SHA256이 모두 같다(`source_hashes.json`).

## 변경

- SDK -6/-7만 최초 요청 뒤 최대 3회 재시도한다. 같은 요청의 4회가 소진되면 새 정책 목표를 만들지 않고 다음 논리 주기로 넘긴다. 같은 축·같은 요청이 5회 연속 실패하거나 해당 축의 정상 응답 공백이 200ms가 되면 HOLD한다. 다른 축의 정상 응답이나 응답 없는 broadcast 송신은 그 축의 읽기 성공으로 계산하지 않는다.
- 응답 ID·길이·체크섬·상태 검증을 유지한다. 재시도는 동일한 절대 목표에 한정한다. 부분 송신, 허용되지 않은 패킷, 모터 상태 오류는 기존처럼 중단한다.
- sync-read에서 뒤 축의 응답까지 소비·검증한 다음 실패한 축만 개별 READ로 재시도한다. RX 잔여 바이트와 모든 송수신 원문·시각을 보존한다. 새 개별 온도 READ의 축별 20ms 간격과 기존 2초 온도 보호는 그대로다.
- HOLD 복구는 최대 5회다. 새 현재 위치 읽기 → 현재 위치 목표 송신 → 주소67 목표 피드백 읽기 → 위치 안정 읽기까지 확인해야 `HOLD_CONFIRMED`다. 포트가 끊겼거나 검증되지 않으면 `HOLD_NOT_CONFIRMED`로 남긴다. 확인 성공이 자동 재개를 허가하지는 않는다.
- `summary.json.communication`에 축별 오류, 발생 시각, 마지막 검증 자세와 그 나이, 손목 각도, 송수신 통계, 중단 상세를 기록한다. broadcast 송신 실패의 대상 축 목록은 실제 개별 응답 오류와 구분한다.
- 팔꿈치만 소프트웨어 보상 누적을 빠르게 했다: gain 0.5→3.0/s, 누적 속도 0.75→4.0°/s, 대기 0.30→0.15초. 요청 상한3°와 한 틱 정수 여유(실제2.912°), 가동범위, 반전 시 감쇠는 유지한다. 모터 PID를 바꾼 것이 아니다.

변경 파일: `live/config.yaml`, `live/config_runtime.py`, `live/communication_retry.py`, `live/deps/direct_live.py`, `live/deps/individual_reply_guard.py`, `live/stream_live.py`, `live/thermal_read.py`, 모의 검사2개, 분석2개, 읽기 전용 계측 도구1개. 기존 파일은 수정 전에 `.bak_20261115_183804` 등 날짜 백업으로 보존했다.

## 오류 분석

보존된 고유 실기 steps 14개에서 재구성 가능한 통신 중단은 ID1 -6 한 건(0스텝), ID5 -7 두 건(1,082스텝 및 이번 1,041스텝)이다. 과거 오류 패킷 원문과 요청별 시각이 없어서 이 값은 전체 wire 오류 횟수가 아니라 실행별 중단 사건 수다.

이번 1,041회 실행 직전 정상 자세는 wrist_roll -2.945°, wrist_flex 42.154°였다. 마지막 두 표본의 속도는 각각 약4.23°/s, 0°/s다. 이전 ID5 중단은 -4.879°/72.484°에서 두 손목 속도가 모두0이었다. 큰 손목 움직임과 오류의 인과관계를 뒷받침하지 않는다. 같은 실패 트랜잭션에서 다른 축도 손상됐는지는 옛 원문이 없어 미확인이다.

고유 steps/readings 17개, 축당11,842표본 범위의 온도 집계:

|---|---:|---:|---:|
| shoulder_pan | 0 | 0 | 37 |

급변 의심은 55°C 미만도 포함하며 실제 과열 확정 횟수가 아니다. 온도 튐이 shoulder_lift에만 생긴 것은 아니다. 최신 thermal_cycle 25개 의심/고온 행에는 같은 묶음에서 여러 축이 동시에 의심으로 판정된 경우가 없었다. 그 밖의 과거 자료는 동시성을 복원할 정보가 부족하다.

이번 실행의 fresh 개별66°C는20.125ms 뒤32°C였다. 당시 shoulder_lift 전압12.1V, 부하-56, 전류1, 토크1, 상태0이었다. 마지막 정상 통신 주기의 전압은6축12.1~12.2V, 온도31~34°C였다. 보고된 전압만으로 전원 처짐이 확인되지는 않았다. 같은 패킷의 전압은 독립 전압계 측정이 아니므로 전원을 배제할 수 없다.

## 실제 READ 교차 비교

움직이지 않는 같은 자세·배선·전원에서 비교했다. 아래 오류는 손상된 응답을 폐기하고 개별 재읽기로 복구한 횟수이며 레지스터 쓰기는0이다.

| 읽기 형식/순서 | 주기 | -6/-7 | 결과 |
|---|---:|---:|---|
| 긴33:38, 1·2·3·4·5·6 | 119 | ID5 -7 41 | 모두 재읽기 복구 |
| 같은 긴 형식 재검사 | 148 | ID5 -7 57 | 모두 재읽기 복구 |
| 긴33:38, 1·2·3·4·6·5 | 296 | 0 | 완료 |
| 같은 변경 순서 재검사 | 493 | ID4 -7 2, ID6 -6 1 | 모두 재읽기 복구 |
| 짧은56:15 + 33:8, 원래 순서 | 296 | 0 | 완료 |
| **배포 형식: 짧은56:15 + 33:8, 1·2·3·4·6·5** | **493** | **0** | **완료** |

긴 패킷의 ID5에서는 본문이 같아도 마지막 체크섬이 정상26에서e6/a6/fe 등으로 달라진 원문이 잡혔다. 읽기 순서·길이에 따른 응답 경계/타이밍 문제가 의심된다. MCU/펌웨어·배선·전원 중 고장 부품 하나를 확정한 결과는 아니다. 정지 중에도 재현되므로 손목 움직임이 필수 원인은 아니다. 다른 축의 드문 오류도 있어 버스/통신 계층을 계속 기록해야 한다.

긴 묶음은 오류를 늘려 **실행기에 채택하지 않았다**. 기존 sync-write 및 짧은 sync-read를 유지하고 읽기 응답 순서만 바꿨다. 관절→ID 대응과 쓰기 목표 순서는 바꾸지 않았다.

배포 형식은 정상 한 주기 기준27 wire 프레임/354바이트(송신9·수신18, 목표1회 포함)다. 50Hz면 약1,350프레임/s,1Mbps의17.7%다. 대역폭 포화라고 단정할 근거는 없다. 이번 실제 읽기만 계측은3,944TX/8,874RX, 평균 작업20.169ms·최대23.903ms, TX 간격 평균2.537ms·최소0.462ms였다. 실제 live 읽기→쓰기 간격은 새 wire 로그로 측정되며 이번에는 live를 하지 않았다.

최종 읽기: 토크6축1, 모드6축0, 온도33/34/32/33/31/35°C, 위치2058/831/3080/2563/1832/465틱. 포트는 닫고 비점유 확인했다. 이 값은 계측 당시 상태다.

## 약통을 못 집은 이유

파란 바구니44회 모두에서 첫 지속 닫힘 후보를 action/state로 찾았다. 후보 시간은4.23~9.40초, 중앙값5.83초다. 대표3회 후보 전후 영상은 별도jpg로 보존했고, 약통 주변에서 닫는 동작임을 확인했다. 아래는 후보의 관절별 중앙값이며, 모든44회에서 실제 집기 성공을 다시 판정한 것은 아니다.

최근 실행의 모델 타임라인은7.493초까지 진행했다. 학습44회 중36회의 닫힘 후보는 그보다 앞이다. **모델 목표 자체가 집기 자세에 도달하지 않았다. 따라서 이번 실패를 서보 추종만의 문제로 설명할 수 없다. 모델 관측/영상 조건과 반복 예측 동작이 조사 대상이다.** 이 비교만으로 특정 카메라가 고장났거나 모델 가중치가 잘못됐다고 확정하지는 않는다.

동시에 팔꿈치 추종도 부족하다: 전송 변화폭3.341°/실제1.055°(31.6%). 당시 보상 최고0.604°였으며 상한3084틱 전송65회, 클리핑76회였다. 범위 비율은 개별 목표의 도달률과 같지 않다. 새 보상이 실제 부하에서 얼마나 좋아지는지는 새 실기 전까지 미확인이다.
