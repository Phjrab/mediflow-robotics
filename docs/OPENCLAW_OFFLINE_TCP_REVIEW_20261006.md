# SO-101 OpenClaw 오프라인 그리퍼 기준점 검토 (2026-10-06)

## 확인한 사실

- 사용자가 보낸 8022 화면에서 천장·사선·손목 프리뷰와 현재 그리퍼의 두 검은 패드가 보인다. 사진만으로 실제 TCP 위치나 깊이를 실측했다고 보지 않는다.
- 로컬 기준 URDF `openclaw_aruco/reference/so101_new_calib.urdf`에는 `gripper` 링크는 있지만 별도 파지 기준 프레임이 없다.
- TheRobotStudio의 SO-101 원본 URDF에는 `gripper_frame_joint`가 있으며, 그리퍼 링크에서 명목상 `[-7.9, -0.218121, -98.1274] mm`, RPY `[0, pi, 0]` 프레임을 정의한다. 출처: https://github.com/TheRobotStudio/SO-ARM100/blob/main/Simulation/SO101/so101_new_calib.urdf
- 원본 URDF와 로컬 URDF는 손목 롤 원점 방향과 일부 관절 한계도 동일하지 않다. 원본의 손목 롤 pitch 0.0486795 rad와 로컬의 거의 0 rad 차이만 고려해도 98 mm 거리에서 약 4.8 mm의 위치 차이가 가능하다. 이는 모델 간 기하 차이에 대한 추정이지 실제 오차 측정값은 아니다.
- LeRobot SO-101 팔 관절은 기본적으로 `use_degrees=True`, 그리퍼는 0–100 모드다. 따라서 기존 계획의 팔 관절 ±100 강제 클리핑은 검증된 물리 제한이 아니었다.

## 오프라인 수정 및 결과

- 명목상 프레임을 별도 JSON으로 기록하고, 원래 URDF나 로봇 보정값은 수정하지 않았다.
- A 에피소드 10의 기존 v2 계획은 원본 팔 관절값 14개를 잘랐다. 생성기 수정 후 새 v3 dry-run은 원본 값을 보존한다. v2 계획은 실제 실행 후보로 사용하지 않는다.
- v3: 1,098개 목표, 20 Hz, 약 54.9초. 이는 녹화 경로 분석값이며 로봇 실행 계획이 아니다.
- 명목상 TCP FK 진단에서 최대 연속 목표 간 거리 약 3.475 mm, 로컬 URDF 한계 초과 Elbow/Wrist_Pitch가 검출되었다. 이 숫자는 작업대 좌표·충돌 안전성을 보증하지 않는다.
- 실행 런타임은 `PHYSICALLY_VALIDATED_SUPERVISED_PATH`, 잔여 차단 사유 0개, TCP/좌표변환/작업영역/관절제한/정지 경로 검증이 없으면 거부하도록 강화했다. 현재 v2/v3 모두 이 조건을 만족하지 않는다.
- 회귀 테스트 `pytest -q openclaw_aruco/tests`: 30 passed.

## 아직 필요한 검증

1. 현재 로봇의 실제 그리퍼 패드 기준 TCP를 현장 보정으로 확인한다. 사진 또는 CAD 수치는 후보일 뿐이다.
2. 독립적인 작업대 점으로 `T_B_W`를 맞추고 보정에 사용하지 않은 점에서 오차를 측정한다.
3. 픽업·접근·투입 높이와 작업영역, 실제 모터 안전 범위를 정한다.
4. 원본 동작/URDF 한계 불일치를 해결하고, 충돌 없는 저속 경로 및 정지 경로를 검증한다.
5. 그 후 별도 감독 시험 범위와 현장 전원 차단 준비를 사용자에게 다시 확인한다.

어떤 자동 로봇 동작도 수행하지 않았다.

## 추가: 현재 follower 보정 범위와 녹화 `action` 대조

- Jetson의 현재 follower 보정 파일을 **읽기만** 했다. 원본 보정값, 로봇 모터, 학습 데이터는 바꾸지 않았다. 범위 tick만 `openclaw_aruco/reference/follower_calibrated_ranges_20261006.json`에 옮겼고 homing offset은 복사하지 않았다.
- 현재 LeRobot의 팔 관절은 degree 모드다. 보정 tick 범위를 degree로 환산하면 Elbow 약 ±97.011°, Wrist Flex 약 ±100.615°다. 이 값은 보정 파일상의 범위이며 검증된 충돌·기계 안전 한계는 아니다. degree 모드의 목표 변환은 이 범위로 자동 클리핑하지 않는다.
- A 에피소드 10 v3 계획 1,098 목표 중 Wrist Flex 86개가 현재 follower 보정 범위를 초과한다(최대 2.154°). 근거: `outputs/openclaw_aruco/plan_a_episode10_follower_range_diagnostic_20261006.json`.
- 기존 60회씩의 A/B/C 데이터 전체도 별도 읽기 전용 진단으로 확인했다. 아래는 해당 관절 범위 초과 **프레임 수 / 영향 받은 에피소드 수**다. 한 프레임에서 두 관절이 함께 초과할 수 있으므로 합계는 고유 프레임 수가 아니다.

| 데이터셋 | 전체 프레임 | Elbow | Wrist Flex |
| --- | ---: | ---: | ---: |
| A (60회) | 32,597 | 11,204 / 54 | 1,335 / 56 |
| B (60회) | 27,613 | 3,665 / 45 | 1,432 / 55 |
| C (60회) | 28,966 | 47 / 3 | 1,341 / 60 |

`outputs/openclaw_aruco/dataset_action_follower_range_audit_20261006.json`에 관절별 최댓값/초과량도 기록했다. 이 데이터는 리더가 만든 과거 `action`을 **오늘의** 팔로워 보정과 비교한 것이다. 과거 녹화가 무효라는 뜻은 아니지만, 저장 동작을 현재 팔로워에 그대로 재생해도 안전하다는 근거로 쓸 수 없다. 로봇 실행 게이트에는 `calibrated_action_range` 검증도 추가했다.

## 추가: 카메라·서비스 확인

- 8022는 정상 응답하고 세 카메라가 8/4/6으로 설정돼 있다. 보정 페이지를 직접 새로고침하고 카메라 스위치를 다시 켜자 천장 프리뷰가 `/camera-snapshot/8` 방식으로 전환돼 `LIVE` 프레임 번호가 다시 증가했다.
- 초기 `/available-cameras` 검사에서 4/6이 빠졌지만, 프리뷰가 V4L2 장치를 점유하면 열기 방식의 장치 검색에서 누락될 수 있다. 이를 곧바로 “카메라 고장”으로 보고하지 않도록 검사 문구를 수정했다. 이후 재검사에는 2/4/6/8이 모두 열거됐다. 열거만으로 모든 프레임의 실시간성을 증명하지는 않는다.
- 현행 8022 텔레옵 상태에는 몸체 시작 차이 제한이 **15°**, Wrist Flex 35°, 그리퍼 20, 제어 20 Hz로 표시된다. 과거 문서의 3°/30 Hz 배포 기록은 현재 설정이 아니다. 현행 제한이 안전하게 검증됐다는 뜻도 아니다.
- 최신 읽기 전용 보고서: `outputs/openclaw_aruco/live_readiness_v4_20261006.json`. 사이트 연결 및 모든 카메라 열거와 별개로 자동 동작은 계속 차단 상태다.
