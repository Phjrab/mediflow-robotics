# 토크 응답 처리 보강 — 2026-11-06

## 확정한 소프트웨어 결함

설치된 파일을 읽어 가짜 포트와 바이트열로 재현했다. 모터·카메라·serial은 열지 않았다.

1. `scservo_sdk/protocol_packet_handler.py:262~280`의 readRx는 ID와 통신 결과를 확인하지만, 응답 데이터 길이가 요청 길이와 같은지 확인하지 않는다.
2. 데이터 없는 정상 체크섬의 ACK를 1바이트 읽기 응답으로 주면, 기존 함수는 ACK의 체크섬을 데이터로 반환했다. 합성 ID1 ACK에서 반환값252를 재현했다. 이 값은 실제 토크값이 아니다.
3. 2바이트짜리 응답을 1바이트 요청의 응답으로 주면 첫 바이트만 반환했다. 지연된 다른 응답을 구분하지 못할 수 있다.
4. `scservo_sdk/group_sync_read.py:58~74`는 readRx의 오류 상태 세 번째 반환값을 버린다. 오류 상태32를 넣어도 통신 성공·값0으로 처리되는 것을 재현했다.

원본 전체 파일 해시는 `source_review/receipt.json`, 필요한 함수와 줄 번호는 `evidence/PROTOCOL_READ_SOURCE.json`에 보존했다. 설치본이나 기존 venv는 수정하지 않았다.

## 이번 현장 중단과의 관계

**위 결함은 확정했지만, 이번 현장 중단의 직접 원인은 여전히 미확인이다.** 당시 원시 응답과 토크값이 기록되지 않아 ACK·긴 응답·모터 오류·실제 토크ON 중 어느 것이었는지 복원할 수 없다. Goal 패킷 뒤에 실제 ACK가 발생했다는 증거도 없다.

Goal_Position의 주소42~43과 Torque_Enable의 주소40은 별개다. [장치 공급사의 ST 메모리 표](https://docs.waveshare.com/Memory_Map_Explanation/ST_Servo_Memory_Map_Explanation)에서도 구분된다. 이것만으로 펌웨어의 부수 효과나 실제 모터 상태를 확정하지 않는다.

같은 ID·같은 데이터 길이의 지연 응답은 이 프로토콜 응답만으로 구분할 수 없다. 이번 보강은 모든 통신 문제 해결이나 실기 정상 판정이 아니다.

## 수정한 것

- `reply_integrity.py`: GroupSyncRead 수신부 앞에서 요청 ID, 정확한 길이, 헤더, 체크섬, 통신 결과, 오류 상태를 검사한다. 잘못된 응답은 값으로 반환하지 않는다.
- 오류 시 원시 바이트, 요청/응답 ID, 요청/응답 길이, 오류 상태를 예외에 담는다. 최근32개 응답까지만 보존한다.
- 한 번 오류가 나면 후속 송수신을 거부한다. 다시 읽어서 정상값으로 덮는 재시도는 없다.
- `trial_runtime.py`: 위 보호를 연결하고 수신 오류의 원문을 결과에 전달한다. 설치된 SDK의 송신 경로·환경·RobotController는 그대로다.
- FIELD_STOP과 초기화 실행 차단, 기존 home·온도·단위·목표 제한은 유지한다. 이번 작업에서는 실제 통신 경로를 실행하지 않았다.

## 관절 오차범위 창

기존 현장 코드의 home 검사는 목표 쓰기 전에 통과했다. 현재 기록에는 관절 고장 또는 home 자세 오류의 증거가 없다. 팔 자세를 맞춘다고 토크 응답 처리 결함이 고쳐지지는 않는다.

`홈_오차범위_전원OFF.html`은 저장된 home 목표만 보여준다. 현재값·차이는 미측정이며 통과 색상을 표시하지 않는다. 브라우저 자동 열기는 현재 주소를 확인하지 못해 중단됐고, 파일은 직접 열 수 있다. 실시간 모니터는 전원을 켜고 모터를 읽어야 하므로 실행하지 않았다.
