# 첫 동작 시험 전 소프트웨어 보완 — 2026-11-06

## 실제 수행

기준 커밋은 `7421db5`이며, 기존 작업 브랜치에서 새 소프트웨어 보완을 준비했다. 이 작업에서는 모터·카메라·serial을 열거나 추론하지 않았다. 레지스터 쓰기, live, 재무장, 설치, 서비스 조작, push는 실행하지 않았다.

| 발견한 문제 | 수정 | 검증 |
|---|---|---|
| 첫 시험은 최대 10스텝인데 clip 비율 감시 창이 20스텝이라 검사에 도달하지 못함 | 감시 창을 `min(20, max_steps)`로 맞춤. 50% 초과 시 해당 목표 송신 전에 HOLD | 최대 10스텝·3스텝 모의 시험에서 조기 중단 |
| 정리 함수 하나가 실패하면 나머지 포트·정책 정리와 결과 저장이 누락될 수 있음 | 자원별 독립 정리, 포트 닫힘 확인, 정리 오류도 HOLD 기록 | 가짜 serial·정책의 정리 오류 주입 |
| 초기 설정 오류가 결과 저장 바깥에서 발생할 수 있음 | 설정 읽기도 결과 보존 범위 안에서 실행 | 장치 생성 전 오류의 RESULT 저장 |
| 정책 생성 중 실패하면 이미 생성된 계산 프로세스가 남을 수 있음 | 생성 실패 시 정리, 중복 정리 방지, 원래 오류 보존 | 가짜 정책·worker 생성/정리 실패 주입 |
| 저장 기록에서 다음에 필요한 증거를 쉽게 구분하기 어려움 | `review_saved_readiness.py` 추가. 최신 기록과 원시 응답을 대조하고 부족한 증거만 보고 | 잘못된 체크섬, 최신 HOLD, 누락된 주소67, 예상 밖 쓰기 기록 검증 |

원래 FIELD_STOP은 덮어쓰지 않는다. live/release 실패 시 중단 파일이 없을 때만 새 파일을 만들며, 기존 파일은 해시만 기록한다. 새 검토 도구는 항상 `live_authorized=false`이고 모터 접근·재무장·중단 해제 기능이 없다.

안전 조건은 유지한다: 30Hz, 첫 시험 최대 10스텝/5초, 관절 1회 0.5도 cap, 초당 20도 제한, 큰 첫 목표 점프 거부, 시작 50도 미만·동작 중 55도 중단, 보정·home·프레임·모델 검증. 기존 RobotController와 LeLab/SDK/가중치/데이터/가상환경은 변경하지 않았다.

## 실제 토크 문제의 현재 판정

- 마지막 확보 기록 `1793945949525475776`은 읽기 54회, 쓰기 0, 토크 6개 OFF, 최고 31도, home 범위 통과다. **현재 실시간 상태가 아닌 저장된 당시 상태다.**
- 당시 주소42 목표는 6개 모두 0이고 현재 위치와 달랐다. 주소67 목표 피드백은 아직 확보하지 못했다. 전원 재투입 뒤의 0만으로 이전 초기화 쓰기의 성공·실패를 단정할 수 없다.
- 과거 불일치의 직접 원인은 여전히 UNVERIFIED다. 앞서 원시 응답 길이·오류 상태 처리 결함은 합성 바이트로 재현하고 보완했지만, 그것이 해당 실기의 원인이라는 증거는 없다.
- 기존 FIELD_STOP은 계속 검토 대상이다. 초기화 도구의 실행 중지와 live 차단은 유지한다. 이번 보완은 이 차단을 해제하지 않는다.
- 공개된 [LeRobot 이슈 #3585](https://github.com/huggingface/lerobot/issues/3585)는 보정 범위를 벗어난 목표 쓰기 후 토크가 켜졌다는 작성자의 사례다. 현재 저장 위치는 보정 범위 안이므로 같은 원인으로 단정하지 않는다. 주소42/67의 의미 대조 근거는 [ST 메모리 표](https://docs.waveshare.com/Memory_Map_Explanation/ST_Servo_Memory_Map_Explanation)다. 실제 펌웨어에서의 동작은 미확인이다.

## 배포 상태와 다음 단계

현재 노트북의 연결 주소 대역과 기존 Jetson 주소 대역이 다르고, ping 및 SSH가 시간 초과됐다. 구체 주소·계정은 이 문서에 기록하지 않았다. 네트워크 설정을 변경하거나 우회 접속하지 않았다.

배포 ZIP은 코드와 검증 목록만 담는다. 기존 4개 파일은 기준 해시가 일치할 때만 백업 후 교체하고, 신규 4개는 기존 파일이 없을 때만 설치한다. FIELD_STOP·데이터·체크포인트·설정·가상환경은 배포 대상이 아니다.

연결 복구 후 진행 순서:

1. Jetson의 저장 진단 파일에서 새 주소67 결과가 생겼는지 확인한다. 장치는 열지 않는다.
2. 중단 파일의 기존 해시와 교체 대상의 기준 해시를 확인한다. 다르면 적용하지 않는다.
3. 새 이름의 백업을 만든 뒤 코드만 배포하고 모의 테스트를 실행한다.
4. 파일 기반 준비 보고와 기본 계획 출력만 실행한다. 모터 쓰기·추론·현장 확인 입력은 하지 않는다.
5. 실제 추가 읽기가 필요하면 운영자가 현장에서 직접 실행한다. 읽기 결과만으로 live를 자동 허가하지 않는다.

```bash

```

롤백은 배포 전 백업에서 교체했던 4개 코드 파일만 복원한다. 새 보조 파일은 실행하지 않은 채 남겨도 된다. FIELD_STOP과 현장 기록은 삭제·되돌리지 않는다. 로컬에서는 새 커밋을 `git revert <이번_커밋>`으로 취소할 수 있다.
